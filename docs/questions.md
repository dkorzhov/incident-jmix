Тикет: DMI-14 (analyst). Каждый вопрос: контекст → пробел/противоречие → варианты → **рекомендация analyst** → адресат/влияние. До решения architect рекомендации считаются рабочими defaults в `docs/requirements.md` и `docs/acceptance-checklist.md`.

Источники: `docs/concept.md` (авторитетный извлечённый текст концепции; извлечён координатором read-only из `IT_Incident_Tracker_Концепция_MVP.docx`, не редактируется analyst), `TASK.md`, `docs/ui-concept.png` (2-страничный рендер концепции с макетами), шаблон Jmix в `src/`.

## Q-01. Jmix User (security-сущность шаблона) vs MVP-пользователь без аутентификации

**Контекст.** Шаблон содержит `entity/User.java` (`inc_User`, UUID PK, username/password, `JmixUserDetails`, `HasTimeZone`), `DatabaseUserRepository`, `UiMinimalRole`/`FullAccessRole`, `LoginView`, `ui.login.defaultUsername=admin`. MVP требует доменного пользователя `{id: int, name, role: engineer|manager}`, селектор в шапке UI и `X-User-Id` в REST; аутентификация вне скоупа (TASK.md §1, §8; концепция §6). TASK.md §1 прямо требует ADR о способе реализации селектора и «текущего пользователя».

**Противоречие.** Security-сущность Jmix (UUID, пароль, роли Spring Security) не совпадает с MVP-контрактом (int id, name, role); стандартный login противоречит «без аутентификации»; REST `/api/**` должен быть permitAll, но UI-операции должны писать актёра = выбранного пользователя, а не `admin`.

**Варианты.**
- A: отдельная доменная сущность (например `inc_AppUser`: int id, name, role) + техническая авто-аутентификация UI-сессии (отключение/обход LoginView, системный пользователь с FullAccessRole); селектор хранит выбранного app-user в Vaadin-сессии; сервисы берут актёра из сессии (UI) или из `X-User-Id` (REST).
- B: переиспользовать `inc_User`, добавив int-идентификатор/role и маппинг — смешивает security и домен, ломает контракт id.
- C: оставить login шаблона как есть — нарушает MVP-требование «выбор из списка без аутентификации».

**Рекомендация:** A. Доменный пользователь отдельной сущностью с int id (контракт REST не меняется); `inc_User` остаётся только техническим для Jmix security; `/api/**` — отдельный `SecurityFilterChain` permitAll (шаблон даёт пример для `/public/**`); ADR фиксирует механизм сессии и актёра. Роль engineer/manager — атрибут домена, не роль Spring Security (прав не различает).
**Адресат:** architect (ADR), backend (security/seed), frontend (селектор). **Влияние:** схема БД, security, UI, seed, тесты.

## Q-02. Генерация ID `INC-NNN`

**Контекст.** TASK.md §1: id — string `INC-NNN`, человекочитаемый, последовательный, генерирует сервер. Концепция и макет используют INC-001…; REST `{id}` — этот же строковый id.

**Пробел.** Не определены: механизм конкурентной генерации (без пропусков/дублей), тип PK в БД (строка vs суррогат + публичный номер), формат при >999, поведение при клиентском `id` в POST.

**Варианты.** DB sequence + форматирование; таблица-счётчик с блокировкой в транзакции; `max(id)+1` (гонки). PK: строковый `INC-NNN` либо UUID/int + отдельный уникальный номер.

**Рекомендация:** последовательность на уровне БД (sequence или счётчик под блокировкой), формат `INC-` + номер с минимум 3 цифрами (INC-1000 допустим, без верхнего предела); PK — строковый id (проще контракт и ссылки history/comments); клиентский `id` в POST игнорировать (или 400 — зафиксировать в контракте); тест BT-34 на конкурентные создания.
**Адресат:** architect (схема), backend. **Влияние:** entity/Liquibase, REST, тесты.

## Q-03. Что считать «значимым изменением» для истории (гранулярность и payload)

**Контекст.** TASK.md §1 задаёт 7 типов событий; §2 — «каждое значимое изменение автоматически пишется в историю»; payload «было/стало». Концепция §2: журнал «создание, назначение, смена статуса, комментарии, решение».

**Пробел.** Не определено: сколько событий порождает комбинированный PATCH (title+priority+assignee); дублируется ли `status_changed` при `resolved`; payload `created` и `commented` (полный текст комментария или ссылка); пишутся ли события при no-op PATCH; считается ли смена assignee через PATCH событием `assigned` (а не `fields_updated`).

**Рекомендация (таблица §6 requirements.md):** по одному событию на тип за операцию; `fields_updated` агрегирует title/description/category; assignee → `assigned`; priority → `priority_changed`; resolve → только `resolved` (со статусом и resolution в before/after); `created` payload = начальные поля («стало»); `commented` payload = `{comment_id, text}` (полный текст, ≤2000 — приемлемо); no-op → 200 без событий; GET событий не пишет. Все события — в той же транзакции, что и изменение.
**Адресат:** architect (контракт payload), backend, QA (BT-20). **Влияние:** сервис истории, тесты payload, UI таб истории.

## Q-04. `resolved_today` и таймзона UTC

**Контекст.** TASK.md §1: `created_at/updated_at` — datetime UTC; §3 dashboard: `resolved_today`. Концепция: «решённые за день». У Incident **нет поля `resolved_at`**; после Closed `updated_at` меняется снова.

**Противоречие/пробел.** «Сегодня» не определено (UTC-сутки vs локальная TZ сервера/пользователя); источник момента resolve не определён (updated_at ненадёжен: закрытие/правки перезаписывают его).

**Варианты.** (a) считать по событиям истории `resolved` с `created_at` ∈ [начало текущих суток UTC, now); (b) добавить колонку `resolved_at` (расширение схемы, не скоупа функциональности); (c) по `updated_at` текущих Resolved — неверно (Closed и правки).

**Рекомендация:** (a) — без изменения схемы, сходится с историей; инцидент, решённый сегодня и затем закрытый, всё равно учитывается в resolved_today; граница суток — UTC (серверное время), не локаль UI. Отображение времени в UI — UTC с пометкой (или локаль браузера — зафиксировать, см. Q-15). Альтернатива (b) допустима, если architect сочтёт агрегаты по истории дорогими; тогда AC-DASH-2 переформулируется на `resolved_at`.
**Адресат:** architect, backend (dashboard), QA (BT-30). **Влияние:** агрегаты dashboard, тесты с controlled clock.

## Q-05. Определения метрик dashboard и графика динамики

**Контекст.** TASK.md §3: counts {open, new, in_progress, critical, resolved_today}, by_priority, recent_activity (10). §4 UI добавляет график динамики; макет: donut/bar по приоритетам (сумма = «всего открытых») и линия «Создано/Решено» по дням (Пн…Вс). Концепция §3: dashboard = counts + диаграмма приоритетов + недавняя активность (динамика есть в макете и TASK.md).

**Пробел.** Не определены: `open` (≠Closed vs New+In Progress), `critical` (все Critical vs только открытые), область `by_priority` (все vs открытые), период и бакеты динамики, состав полей recent_activity.

**Рекомендация:** open = status ≠ Closed; new = New; in_progress = In Progress; critical = Critical ∧ ≠ Closed; by_priority — по открытым (сумма = open, сходится с макетом); динамика — последние 7 суток UTC, два ряда: создано (created_at) и решено (события `resolved`), бакет = сутки UTC; recent_activity = 10 последних событий истории desc с {incident_id, incident_title?, actor_name, type, payload, created_at}. Данные динамики: отдельное поле dashboard-ответа либо вычисление UI из API — зафиксировать в контракте (предложение: поле `dynamics` в GET /api/dashboard, чтобы UI не делал N запросов).
**Адресат:** architect (контракт), backend, frontend (Charts), QA (BT-30, UT-05). **Влияние:** сходимость KPI, тесты.

## Q-06. `X-User-Id`: обязательность на GET и код ошибки

**Контекст.** TASK.md §3: `/api/**` без аутентификации; текущий пользователь — `X-User-Id`, валидируется против users. Коды 400/409 заданы, код для отсутствующего/неизвестного заголовка — нет; не сказано, нужен ли заголовок на GET.

**Пробел.** Матрица «метод × обязательность заголовка × код ошибки» не определена; контракт «идентичен проекту incident», но его текст недоступен в этом репо.

**Варианты.** (a) обязателен на всех /api/**; (b) обязателен только на mutating (POST/PATCH), GET публичные; (c) обязателен на mutating, на GET — опционален, но если передан, валидируется.

**Рекомендация:** (c): mutating без/с неизвестным заголовком → **401** `{detail}`; GET допускает отсутствие (read-only), неизвестное значение → 401. Единая валидация против GET /api/users. Зафиксировать в API-контракте ADR и отразить в AC-LIST-6/AC-CREATE-4 и т.д.
**Адресат:** architect (контракт), backend, QA. **Влияние:** все эндпоинты, тесты 401.

## Q-07. Неизвестный id инцидента и отсутствие DELETE

**Контекст.** TASK.md §3 не задаёт ответ для несуществующего `{id}`; §2/§8: удаления нет, DELETE-эндпоинта нет.

**Пробел.** Коды 404 (неизвестный id) и поведение DELETE (405 vs 404) не зафиксированы.

**Рекомендация:** неизвестный/несуществующий id на GET/PATCH/POST comments → **404** `{detail}`; DELETE → **405** (эндпоинт не объявлен) либо 404 — зафиксировать одно; данные никогда не удаляются. Добавить в контракт и тесты BT-08/BT-32.
**Адресат:** architect, backend, QA. **Влияние:** контракт ошибок, тесты.

## Q-08. Редактируемость `resolution` и отсутствие reopen

**Контекст.** PATCH §3 принимает только {title, description, category, priority, assignee_id} — resolution вне списка; resolution обязателен при переходе в Resolved. Автомат не содержит обратных переходов.

**Пробел.** Можно ли править resolution после Resolved (до Closed)? Что делать с `resolution` в теле `/status` при переходе не в Resolved? Допустим ли reopen (Resolved→In Progress)?

**Рекомендация:** resolution — write-once при переходе в Resolved, далее read-only (правка возможна только новым resolve-переходом, которого автомат не допускает); `resolution` при переходе не в Resolved игнорировать (или 400 — зафиксировать); reopen вне MVP (409). UI показывает resolution read-only. Если бизнесу нужна правка решения — отдельное расширение скоупа, не MVP.
**Адресат:** architect, backend, frontend. **Влияние:** PATCH-контракт, UI карточки, тесты.

## Q-09. Семантика `updated_at` при комментарии и no-op PATCH

**Контекст.** `updated_at` — «серверное время» последнего изменения; комментарий — дочерняя сущность; no-op PATCH не меняет полей.

**Пробел.** Трогает ли комментарий `updated_at` инцидента? Меняется ли `updated_at` при no-op PATCH?

**Рекомендация:** `updated_at` обновляется только при изменении собственных полей инцидента (поля/статус/assignee/resolution); комментарий его не трогает (активность видна по истории); no-op PATCH не меняет `updated_at` и не пишет историю. Зафиксировать в контракте, чтобы тесты сходимости не плавали.
**Адресат:** architect, backend, QA. **Влияние:** BT-09/BT-20, сортировки.

## Q-10. Формат `detail` в ошибках 400

**Контекст.** TASK.md §2: «валидация полей → 400 с указанием полей и причин»; §3: «ошибки — JSON `{detail: ...}` с понятным текстом».

**Пробел.** `detail` — строка с перечислением полей/причин или структурированный объект {field: reason}? UI должен показывать понятный текст; клиентская валидация покрывает только title.

**Рекомендация:** `detail` — человекочитаемая строка вида `"title: длина 5–120 символов; priority: неизвестное значение"` (поля и причины перечислены); ключ всегда `detail`; UI выводит текст как есть в notification. Структурированный вариант допустим только если architect зафиксирует его в контракте и UI научится рендерить поля; строка — минимальный совместимый default.
**Адресат:** architect (контракт), backend, frontend, QA (BT-33). **Влияние:** все 400/401/404/409.

## Q-12. Стек и «одна команда запуска» концепции vs Jmix-версия (разрешено)

**Контекст.** Концепция §5: FastAPI/React/Alembic/pytest; §7: «приложение запускается одной командой docker compose up». TASK.md §0/§6 и тикет: стек зафиксирован Jmix 3.1/Gradle/Liquibase; запуск = `docker compose up -d db` + `./gradlew bootRun`.

**Противоречие.** Формально «при расхождении приоритет у концепции», но концепция описывает исходный проект `incident`; тикет и AGENTS.md прямо фиксируют Jmix-стек и называют требования идентичными по бизнес-части.

**Рекомендация (считаем разрешённым):** приоритет концепции применять к бизнес-правилам/функциональности; стек и процедура запуска — по TASK.md §0/§6 (зафиксированы тикетом). DoD-пункт «запуск» проверять по TASK.md §7 (db + bootRun), не по «одной команде» концепции. Полноценный docker-compose приложения (app+db одной командой) — вне скоупа MVP. Зафиксировать это толкование в ADR, чтобы следующие агенты не «чинили» стек по концепции.
**Адресат:** architect (ADR), все. **Влияние:** DoD-чек-лист п.1, README.

## Q-13. Текущий пользователь в UI: default, хранение, актёр операций

**Контекст.** Селектор в шапке (макет: «Иван Петров»). Не определено: кто выбран при первом входе, где хранится выбор, как UI-операции получают актёра (UI работает через сервисы Jmix, не через REST).

**Пробел.** Default-пользователь; персистентность выбора между видами/сессиями; механизм передачи актёра в сервисы (иначе история будет писать `admin`).

**Рекомендация:** default = первый пользователь списка (стабильный порядок по id); выбор хранится в Vaadin-сессии (переживает навигацию, не требует БД); сервисный слой принимает актёра параметром/из контекста: UI подставляет выбранного, REST — из `X-User-Id`; ADR (Q-01) фиксирует механизм. Тест UT-06 проверяет смену актёра.
**Адресат:** architect (ADR), frontend, backend. **Влияние:** MainView, сервисы, история, тесты.

## Q-14. Состав demo-seed

**Контекст.** TASK.md §6: `SEED_DEMO=true` — 3–5 пользователей, несколько инцидентов в разных статусах, включая Critical и решённый сегодня. Макет даёт имена: Иванов И.И., Петров П.П., Сидоров А.А.; шапка — Иван Петров.

**Пробел.** Конкретный состав не задан; «решённый сегодня» должен быть корректен относительно UTC-суток и истории (событие `resolved` сегодня).

**Рекомендация:** 4 пользователя: Иванов И.И. (engineer), Петров П.П. (engineer), Сидоров А.А. (engineer), Кузнецова М.М. (manager); 6 инцидентов: New (Critical, «Проблемы с VPN»), New (Medium), In Progress (High, «Не работает почта»), In Progress (Critical, «Медленно работает БД»), Resolved сегодня (High, с resolution и событием `resolved` сегодня UTC), Closed (Low, полная история цикла); комментарии и история согласованы с статусами; seed идемпотентен (повторный запуск не дублирует). Состав фиксируется backend, проверяется BT-35.
**Адресат:** backend (seed), QA. **Влияние:** демо-приёмка, dashboard resolved_today.

## Q-15. Мелкие контрактные defaults (зафиксировать одним списком в ADR)

**Контекст/пробелы.** Не определены: код успеха POST (201 vs 200); семантика `q` (регистр, подстрока, поиск по числовой части id); tie-break сортировки при равных created_at; неизвестные поля в теле POST/PATCH (игнор vs 400); неизвестные значения фильтров `status`/`priority` в GET /api/incidents; порядок comments/history в карточке; язык UI и отображение времени.

**Рекомендация:** POST/POST comments → **201** с телом объекта; `q` — регистронезависимая подстрока по id и title; неизвестное значение фильтра status/priority → 400 с указанием параметра; сортировка `created_at desc, id desc`; неизвестные поля тела игнорируются (кроме `id` — см. Q-02); history — новые сверху, comments — хронологически (старые сверху); UI — ru (метки макета), время отображать в UTC с пометкой «UTC» (единообразно с API); локали en,ru сохранены для сообщений Jmix. Все пункты — defaults до фиксации в API-контракте ADR.
**Адресат:** architect (контракт), backend, frontend, QA. **Влияние:** BT-33, UT-01…05, E2E-01.
