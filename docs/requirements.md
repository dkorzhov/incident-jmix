## 1. Роли и персоны

Доменная роль пользователя (`engineer`, `manager`) — **информационный атрибут**: в MVP права не различаются (авторизация вне скоупа). Персоны ниже описывают сценарии использования, а не разрешения.

| Персона | Кто | Основные сценарии |
|---|---|---|
| Оператор | сотрудник ИТ-службы, регистрирует обращения | реестр, поиск/фильтры, создание инцидента, просмотр карточки |
| Инженер | исполнитель (`engineer`) | назначение себя/другого, «Взять в работу», комментарии, resolve с resolution, правка полей |
| Менеджер | руководитель (`manager`) | dashboard и аналитика, контроль статусов, «Закрыть», просмотр истории и списка пользователей |

Текущий пользователь в UI выбирается из предзагруженного списка (селектор в шапке); в REST передаётся заголовком `X-User-Id`. Все действия фиксируют актёра = текущий пользователь.

## 2. User stories

Формат: «Как <роль>, я хочу <действие>, чтобы <ценность>». Критерии приёмки (AC) даны кратко; полные проверяемые критерии по эндпоинтам — §5, по UI — §7.

### US-01 Реестр инцидентов (оператор)
Как оператор, я хочу видеть список всех инцидентов с поиском и фильтрами, чтобы быстро находить нужное обращение.
- AC: таблица содержит ID, название, приоритет (цветной бейдж), статус (бейдж), ответственного; сортировка `created_at desc`.
- AC: поиск `q` находит по ID и по названию (регистронезависимая подстрока); фильтры статуса и приоритета комбинируются с поиском (логическое И).
- AC: над таблицей — KPI-карточки (концепция §3 «Реестр»: заголовок, KPI-карточки, поиск, фильтры, таблица, кнопка).
- AC: пустой результат поиска/фильтра и пустой реестр показывают пустое состояние с текстом, а не пустую таблицу молча.
- AC: список без пагинации (§8).
- См. AC-LIST-1…AC-LIST-6, UI-1.

### US-02 Создание инцидента (оператор)
Как оператор, я хочу зарегистрировать инцидент с названием, описанием, категорией, приоритетом и необязательным ответственным, чтобы проблема попала в единый реестр.
- AC: сервер генерирует человекочитаемый последовательный ID `INC-NNN` (INC-001, INC-002, …); клиент ID не задаёт.
- AC: статус нового инцидента = `New`; `created_at`/`updated_at` = серверное время UTC.
- AC: в истории автоматически событие `created` с payload начальных полей; актёр = текущий пользователь.
- AC: невалидные поля → 400 с указанием полей и причин; UI показывает ошибку понятным текстом.
- См. AC-CREATE-1…AC-CREATE-6, UI-3.

### US-03 Карточка инцидента (инженер)
Как инженер, я хочу открыть карточку с деталями, табами «Информация / История / Комментарии», чтобы видеть контекст проблемы.
- AC: карточка показывает номер + название, бейджи статуса/приоритета, категорию, описание, ответственного, даты создания/обновления, resolution (если есть).
- AC: ответ API карточки включает comments и history одним запросом.
- AC: неизвестный ID → 404 с понятным текстом (см. Q-07).
- См. AC-GET-1…AC-GET-4, UI-2.

### US-04 Назначение ответственного (инженер/менеджер)
Как инженер, я хочу назначить ответственного (в том числе себя) или снять назначение, чтобы у проблемы был владелец.
- AC: смена `assignee_id` через PATCH и через селектор в карточке; допустимо `null` (снять).
- AC: каждое изменение назначения → событие `assigned` с payload «было/стало».
- AC: `assignee_id` вне списка пользователей → 400.
- См. AC-PATCH-4, AC-PATCH-6, US-13.

### US-05 Взять в работу (инженер)
Как инженер, я хочу перевести инцидент New → In Progress кнопкой «Взять в работу», чтобы зафиксировать начало обработки.
- AC: переход разрешён только из `New`; событие `status_changed` («было/стало»).
- AC: иные переходы в In Progress → 409.
- См. AC-STATUS-1, AC-STATUS-5.

### US-06 Решить инцидент (инженер)
Как инженер, я хочу отметить инцидент решённым с обязательным описанием решения, чтобы зафиксировать результат обработки.
- AC: переход In Progress → Resolved возможен только с непустым `resolution` (1–2000 симв., не только пробелы).
- AC: без resolution / пустой resolution → 400; UI-форма resolve делает поле обязательным.
- AC: событие `resolved` с payload «было/стало» включая resolution.
- См. AC-STATUS-2, AC-STATUS-3, AC-STATUS-6.

### US-07 Закрыть инцидент (менеджер)
Как менеджер, я хочу закрыть решённый инцидент, чтобы зафиксировать завершение цикла.
- AC: переход Resolved → Closed кнопкой «Закрыть»; событие `status_changed`.
- AC: закрытие напрямую из New/In Progress невозможно → 409 (и в UI кнопка не показывается).
- AC: после Closed инцидент неизменяем: PATCH, смена статуса, комментарии → 409; UI read-only.
- См. AC-STATUS-4, AC-STATUS-7, AC-PATCH-7, AC-COMMENT-4.

### US-08 Комментарии (инженер)
Как инженер, я хочу добавлять комментарии к инциденту, чтобы фиксировать ход работ.
- AC: автор = текущий пользователь (`X-User-Id` / селектор UI), текст 1–2000 симв., `created_at` серверный UTC.
- AC: комментарии доступны во всех статусах кроме Closed; событие `commented` в истории.
- AC: пустой/слишком длинный текст → 400; комментарий к Closed → 409.
- См. AC-COMMENT-1…AC-COMMENT-5.

### US-09 История изменений (инженер/менеджер)
Как менеджер, я хочу видеть автоматический журнал изменений инцидента, чтобы понимать, кто и что менял.
- AC: история пишется сервером автоматически при каждом значимом изменении (§6), без действий пользователя.
- AC: каждое событие содержит тип, актёра, время UTC и payload «было/стало» (для `created`/`commented` — «стало»).
- AC: таб «История» показывает события с человекочитаемым описанием и актёром.
- См. AC-HIS-1…AC-HIS-4, §6.

### US-10 Dashboard (менеджер)
Как менеджер, я хочу видеть KPI, диаграмму по приоритетам, график динамики и недавнюю активность, чтобы оценивать нагрузку команды.
- AC: KPI: открытые, новые, в работе, критические, решено сегодня; значения сходятся с данными БД на момент запроса.
- AC: диаграмма по приоритетам и график динамики рендерятся Charts add-on (Apache ECharts).
- AC: недавняя активность = последние 10 событий истории по всем инцидентам.
- AC: пустые данные → пустое состояние/нулевые KPI, без ошибок рендера.
- См. AC-DASH-1…AC-DASH-6, UI-4.

### US-11 Список пользователей (менеджер)
Как менеджер, я хочу видеть предзагруженный список пользователей, чтобы знать состав команды и выбирать ответственного/текущего пользователя.
- AC: экран «Пользователи» — просмотр списка (id, name, role); редактирование не предусмотрено.
- См. AC-USERS-1…AC-USERS-2, UI-5.

### US-12 Селектор текущего пользователя (все)
Как пользователь MVP, я хочу выбрать себя из списка в шапке, чтобы действия фиксировались от моего имени без аутентификации.
- AC: селектор в шапке MainView содержит всех пользователей; выбор действует для всех последующих операций UI (актёр истории/комментариев = выбранный).
- AC: REST принимает текущего пользователя заголовком `X-User-Id`, валидируемым против списка users.
- AC: механизм «текущего пользователя» без аутентификации в Jmix фиксируется в ADR (TASK.md §1; см. Q-01, Q-13).
- См. AC-USERS-3, AC-HEADER-1…AC-HEADER-3.

### US-13 Правка полей инцидента (инженер)
Как инженер, я хочу исправить название, описание, категорию, приоритет до закрытия инцидента, чтобы данные оставались актуальными.
- AC: PATCH принимает частичное обновление перечисленных полей; неизменённые поля не трогаются.
- AC: смена приоритета → событие `priority_changed`; правка title/description/category → `fields_updated` с payload «было/стало» только изменённых полей.
- AC: валидация длин/enum → 400 с полями и причинами; PATCH к Closed → 409.
- См. AC-PATCH-1…AC-PATCH-8.

### US-14 Защита от недопустимых операций (все)
Как пользователь, я хочу, чтобы сервер блокировал недопустимые переходы и правки закрытых инцидентов, чтобы данные не противоречили бизнес-правилам.
- AC: все проверки §4 выполняются на backend, а не только в UI (прямой вызов REST обходит UI — правила всё равно срабатывают).
- AC: UI показывает только допустимые действия, но серверная защита независима от UI.
- AC: удаление инцидентов невозможно: DELETE-эндпоинта нет.
- См. AC-STATUS-5, AC-PATCH-7, AC-COMMENT-4, AC-DEL-1.

### US-15 Понятные ошибки и пустые состояния (все)
Как пользователь, я хочу видеть понятные сообщения об ошибках и пустых списках, чтобы понимать, что происходит.
- AC: ошибки сервера (400/401/404/409) отображаются в UI понятным текстом (notification/сообщение), не молча.
- AC: клиентская валидация длины title (5–120) в форме создания срабатывает до отправки.
- AC: пустые состояния: реестр, результат поиска, комментарии, история, dashboard без данных, список пользователей.
- См. UI-1…UI-6, AC-ERR-1.

## 3. Требования по сущностям

### 3.1 Incident

| Поле | Тип/ограничения | Требования |
|---|---|---|
| id | string `INC-NNN` | человекочитаемый, последовательный (INC-001…), генерирует сервер; уникален; используется в URL `/api/incidents/{id}`; клиент не задаёт (FR-ID; Q-02) |
| title | string, 5–120 симв. | обязателен; обрезка пробелов по краям не должна обходить минимум (значение из пробелов → 400) |
| description | string, 0–2000 симв. | необязателен (пустая строка допустима) |
| category | enum | `Network`, `Mail`, `Portal`, `Database`, `Workplace`, `Other`; обязателен при создании |
| priority | enum | `Critical`, `High`, `Medium`, `Low`; обязателен при создании |
| status | enum | `New`, `In Progress`, `Resolved`, `Closed`; при создании всегда `New`; меняется только по автомату §4 |
| assignee_id | int \| null | ссылка на пользователя из списка; необязателен; `null` = не назначен |
| resolution | string \| null, 0–2000 симв. | обязателен непустой при переходе в Resolved; write-once при resolve (предложение, Q-08); вне перехода в Resolved не редактируется через PATCH (контракт §3 PATCH его не содержит) |
| created_at | datetime UTC | серверное время создания, неизменяемо |
| updated_at | datetime UTC | серверное время последнего значимого изменения инцидента (семантика при комментарии — Q-09) |

Инварианты:
- FR-1: удаление инцидентов не предусмотрено (нет DELETE-эндпоинта, нет UI-действия).
- FR-2: Closed ⇒ неизменяемость всех полей, статуса и комментариев.
- FR-3: каждое значимое изменение (§6) порождает ровно одно событие истории соответствующего типа в той же транзакции, что и изменение.
- FR-4: все бизнес-проверки выполняются на backend (сервисный слой), UI лишь дублирует удобство.
- FR-5: длины и enum-значения валидируются на backend независимо от UI.

### 3.2 User (предзагруженный список)

| Поле | Тип | Требования |
|---|---|---|
| id | int | стабильный идентификатор; используется в `assignee_id`, `author_id`, `actor_id`, `X-User-Id` |
| name | string | отображаемое имя (например «Иванов И.И.») |
| role | enum | `engineer`, `manager`; информационный атрибут, прав не различает (MVP) |

- FR-6: список предзагружен (Liquibase/seed); создание/редактирование пользователей через UI/API не предусмотрено.
- FR-7: `X-User-Id` и `assignee_id` валидируются против этого списка (неизвестный id → ошибка, §5).
- FR-8: соотношение с security-сущностью шаблона Jmix `inc_User` (UUID, username/password, `JmixUserDetails`) и механизм «текущего пользователя» без аутентификации — решение architect в ADR (Q-01). Требования MVP не меняются: доменный пользователь имеет int id, name, role.

### 3.3 Comment

| Поле | Тип | Требования |
|---|---|---|
| id | int (суррогатный) | генерирует сервер |
| incident_id | ссылка | обязателен; инцидент существует |
| author_id | int | = текущий пользователь (`X-User-Id`), не передаётся клиентом в теле |
| text | string, 1–2000 симв. | обязателен, не только пробелы |
| created_at | datetime UTC | серверное время |

- FR-9: комментарии нельзя добавлять к Closed (409); редактирование/удаление комментариев не предусмотрено контрактом.
- FR-10: добавление комментария порождает событие `commented`.

### 3.4 HistoryEvent

| Поле | Тип | Требования |
|---|---|---|
| id | int (суррогатный) | генерирует сервер |
| incident_id | ссылка | обязателен |
| actor_id | int | текущий пользователь на момент изменения |
| type | enum | `created`, `assigned`, `status_changed`, `priority_changed`, `commented`, `resolved`, `fields_updated` |
| payload | json | «было/стало» (§6); для `created`/`commented` — только «стало» |
| created_at | datetime UTC | серверное время события |

- FR-11: история пишется только сервером автоматически; API/UI не позволяют создавать/править/удалять события.
- FR-12: события упорядочиваемы по `created_at` (и id как tie-breaker); `recent_activity` dashboard = последние 10 событий по всем инцидентам.

## 4. Бизнес-правила (автомат статусов)

```
New         → In Progress   («Взять в работу»)
In Progress → Resolved      (обязателен непустой resolution)
Resolved    → Closed        («Закрыть»)
```

| Правило | Ответ сервера |
|---|---|
| BR-1: переход не из списка разрешённых (включая New→Resolved, New→Closed, In Progress→Closed, обратные переходы, переход в тот же статус) | **409** `{detail}` |
| BR-2: переход в Resolved без resolution / с пустым (пробельным) resolution | **400** `{detail}` |
| BR-3: resolution длиннее 2000 симв. | **400** |
| BR-4: любое изменение Closed-инцидента (PATCH полей, PATCH статуса, комментарий) | **409** |
| BR-5: нарушение длин/обязательности/enum полей | **400** с указанием полей и причин |
| BR-6: неизвестный `assignee_id` / неизвестный `X-User-Id` | ошибка валидации ссылки (код для X-User-Id — Q-06; для assignee_id — 400) |
| BR-7: удаление инцидента | эндпоинта нет (405/404, Q-07) |
| BR-8: каждое значимое изменение → автозапись в историю (§6) | — |

Различение 400 и 409 для `/status`: неизвестное/невалидное значение статуса или нарушение полей → 400; известное допустимое enum-значение, но недопустимый переход → 409.

## 5. Критерии приёмки по эндпоинтам (TASK.md §3)

Общие требования ко всем эндпоинтам:
- AC-COMMON-1: ответы JSON в **snake_case**; ошибки — `{ "detail": ... }` с понятным текстом (формат detail — Q-10).
- AC-COMMON-2: `/api/**` доступны без аутентификации; текущий пользователь — заголовок `X-User-Id`, валидируется против списка users (обязательность на GET — Q-06).
- AC-COMMON-3: все временные метки в ответах — UTC (ISO-8601).
- AC-COMMON-4: серверные проверки срабатывают при прямом вызове REST без UI.

### GET /api/incidents — список
- **AC-LIST-1 (успех):** 200; массив инцидентов, сортировка `created_at desc`; без пагинации; поля в snake_case (`id, title, description, category, priority, status, assignee_id, resolution, created_at, updated_at`).
- **AC-LIST-2 (поиск):** `?q=` фильтрует по подстроке ID и title, регистронезависимо; `q=INC-001` и `q=почта` находят соответствующие записи.
- **AC-LIST-3 (фильтры):** `?status=` и `?priority=` принимают enum-значения; комбинируются между собой и с `q` (И); неизвестное значение фильтра → 400 с указанием поля (предложение, Q-15).
- **AC-LIST-4 (пусто):** нет совпадений → 200 и пустой массив (не 404).
- **AC-LIST-5 (история):** чтение список не порождает событий истории.
- **AC-LIST-6 (X-User-Id):** поведение при отсутствии/неизвестном заголовке — по Q-06 (предложение: GET допускает отсутствие, неизвестное значение → 401).

### POST /api/incidents — создание
- **AC-CREATE-1 (успех):** 201 (или 200 — фиксирует architect, Q-15) с телом созданного инцидента; `id` формата `INC-NNN`, следующий по порядку; `status=New`; `created_at=updated_at` = серверное UTC; `assignee_id` = переданный или null.
- **AC-CREATE-2 (валидация 400):** title короче 5 / длиннее 120 / отсутствует / пробельный; description > 2000; неизвестные category/priority; отсутствующие обязательные category/priority; `assignee_id` вне списка users → 400 `{detail}` с перечислением полей и причин; инцидент не создаётся.
- **AC-CREATE-3 (история):** ровно одно событие `created`, actor = `X-User-Id`, payload «стало» = начальные поля (title, description, category, priority, status, assignee_id).
- **AC-CREATE-4 (X-User-Id 401):** отсутствующий/неизвестный `X-User-Id` → 401 `{detail}` (предложение, Q-06); инцидент не создаётся, история не пишется.
- **AC-CREATE-5 (id):** клиентский `id` в теле игнорируется/отклоняется (фиксирует architect, Q-15); последовательность не пропускает номера при конкурентных созданиях (Q-02).
- **AC-CREATE-6 (409 неприменим):** создание не зависит от статусов; 409 не возвращается.

### GET /api/incidents/{id} — карточка
- **AC-GET-1 (успех):** 200; поля инцидента + `comments` (массив с author/text/created_at) + `history` (массив событий с type/actor/payload/created_at); одним запросом.
- **AC-GET-2 (404):** неизвестный id (в т.ч. несуществующий `INC-999`) → 404 `{detail}` (Q-07).
- **AC-GET-3 (порядок):** comments и history упорядочены по времени (предложение: history — новые сверху, comments — хронологически; фиксирует architect, Q-15).
- **AC-GET-4 (история/ Closed):** чтение не меняет данные и не пишет историю; Closed-инцидент читается полностью.

### PATCH /api/incidents/{id} — правка полей
- **AC-PATCH-1 (успех):** 200; обновлены только переданные поля из {title, description, category, priority, assignee_id}; `updated_at` обновлён; ответ — актуальное состояние.
- **AC-PATCH-2 (валидация 400):** нарушения длин title/description, неизвестные enum, неизвестный assignee_id → 400 с полями и причинами; данные не меняются, история не пишется.
- **AC-PATCH-3 (частичность):** отсутствие поля в теле = поле не меняется; `assignee_id: null` снимает назначение.
- **AC-PATCH-4 (история assigned):** смена assignee_id → событие `assigned`, payload `{before:{assignee_id:…}, after:{assignee_id:…}}`.
- **AC-PATCH-5 (история priority/fields):** смена priority → `priority_changed`; изменение title/description/category → `fields_updated` с «было/стало» только изменённых полей; комбинированный PATCH порождает события по каждому типу (Q-03).
- **AC-PATCH-6 (no-op):** PATCH без фактических изменений → 200, события истории не пишутся (предложение, Q-03).
- **AC-PATCH-7 (Closed 409):** любой PATCH к Closed → 409, данные неизменны.
- **AC-PATCH-8 (404/401):** неизвестный id → 404; отсутствующий/неизвестный `X-User-Id` → 401 (Q-06/Q-07).

### PATCH /api/incidents/{id}/status — автомат
- **AC-STATUS-1 (успех New→In Progress):** 200; статус изменён; событие `status_changed` с «было/стало»; actor = X-User-Id.
- **AC-STATUS-2 (успех In Progress→Resolved):** 200 при непустом resolution ≤2000; resolution сохранён; событие `resolved` с «было/стало» включая resolution и статус.
- **AC-STATUS-3 (400 resolve без resolution):** отсутствие/пустой/пробельный resolution → 400; статус не меняется; история не пишется.
- **AC-STATUS-4 (успех Resolved→Closed):** 200; событие `status_changed`; после этого инцидент неизменяем.
- **AC-STATUS-5 (409 переходы):** New→Closed, New→Resolved, In Progress→Closed, Resolved→In Progress, Resolved→New, Closed→любой, переход в тот же статус → 409 `{detail}`; данные и история не меняются.
- **AC-STATUS-6 (400 валидация):** неизвестное значение status, resolution > 2000 → 400 (а не 409).
- **AC-STATUS-7 (Closed 409):** PATCH статуса Closed-инцидента → 409 независимо от целевого статуса.
- **AC-STATUS-8 (404/401):** неизвестный id → 404; отсутствующий/неизвестный X-User-Id → 401 (Q-06/Q-07).
- **AC-STATUS-9 (resolution вне перехода):** передача resolution при переходе не в Resolved игнорируется или 400 (фиксирует architect, Q-08); resolution не создаёт отдельного события кроме `resolved`.

### POST /api/incidents/{id}/comments — комментарий
- **AC-COMMENT-1 (успех):** 201/200 (Q-15); комментарий с author = текущий пользователь (не из тела), text, created_at UTC; виден в карточке.
- **AC-COMMENT-2 (400):** text отсутствует/пустой/пробельный/длиннее 2000 → 400 с указанием поля; комментарий не создаётся.
- **AC-COMMENT-3 (история):** событие `commented` с actor и payload (comment_id + text, Q-03).
- **AC-COMMENT-4 (Closed 409):** комментарий к Closed → 409.
- **AC-COMMENT-5 (404/401):** неизвестный incident id → 404; отсутствующий/неизвестный X-User-Id → 401 (Q-06/Q-07).

### GET /api/dashboard — показатели
- **AC-DASH-1 (успех):** 200; `counts: {open, new, in_progress, critical, resolved_today}`, `by_priority`, `recent_activity` (последние 10 событий истории, новые сверху, с incident id, актёром, типом, payload, временем).
- **AC-DASH-2 (сходимость с БД):** каждое значение counts равно агрегату по БД на момент запроса: `new` = статус New; `in_progress` = In Progress; `open` = не Closed (предложение, Q-05); `critical` = priority Critical и не Closed (Q-05); `resolved_today` = переходы в Resolved за текущие сутки UTC (Q-04).
- **AC-DASH-3 (by_priority):** количество по каждому приоритету в области «открытые» (не Closed) — предложение, Q-05; сумма by_priority = open.
- **AC-DASH-4 (динамика):** данные для графика динамики (создано/решено по дням) доступны API или вычисляются UI из данных БД; период и источник — Q-05 (предложение: последние 7 суток UTC, created_at и события resolved).
- **AC-DASH-5 (recent_activity):** ровно ≤10 событий, сортировка created_at desc по всем инцидентам; включает события всех типов; после нового изменения инцидента список обновляется.
- **AC-DASH-6 (пусто):** пустая БД → нулевые counts, пустые by_priority/recent_activity, 200 без ошибок.
- **AC-DASH-7 (история):** чтение dashboard не пишет историю.

### GET /api/users — пользователи
- **AC-USERS-1 (успех):** 200; массив `{id, name, role}` предзагруженных пользователей; role ∈ {engineer, manager}.
- **AC-USERS-2 (состав):** список совпадает с используемым в селекторе UI и в валидации X-User-Id/assignee_id (единый источник).
- **AC-USERS-3 (X-User-Id):** валидация заголовка выполняется против этого же списка.

### Отсутствие DELETE
- **AC-DEL-1:** DELETE-эндпоинта `/api/incidents/{id}` нет; запрос DELETE не удаляет данные (405/404, Q-07); UI не содержит действия удаления.

### Общие критерии ошибок и истории
- **AC-ERR-1:** все ошибки — JSON `{detail}` с понятным текстом; 400 перечисляет поля и причины; UI отображает текст ошибки пользователю (notification), не молча.
- **AC-HIS-1:** каждое значимое изменение (§6) порождает событие в той же транзакции; при ошибке (400/401/404/409) событие не пишется.
- **AC-HIS-2:** payload содержит «было/стало» для changed-типов; значения до и после совпадают с фактическим состоянием до/после операции.
- **AC-HIS-3:** actor_id = текущий пользователь операции (X-User-Id в REST; выбранный в селекторе пользователь в UI).
- **AC-HIS-4:** события истории неизменяемы и не удаляются; порядок стабилен (created_at, id).
- **AC-HEADER-1:** селектор UI содержит всех пользователей из GET /api/users (единый источник).
- **AC-HEADER-2:** выбор пользователя в селекторе меняет актёра всех последующих UI-операций (комментарии, история).
- **AC-HEADER-3:** механизм сессии/подстановки пользователя в Jmix без аутентификации зафиксирован в ADR (Q-01).

## 6. «Значимые изменения» и payload истории

Предлагаемая гранулярность (окончательно фиксирует architect, Q-03):

| Операция | Тип события | payload (предложение) |
|---|---|---|
| POST /incidents | `created` | `{after: {title, description, category, priority, status:"New", assignee_id}}` |
| смена assignee (PATCH или UI) | `assigned` | `{before:{assignee_id}, after:{assignee_id}}` |
| New→In Progress, Resolved→Closed | `status_changed` | `{before:{status}, after:{status}}` |
| смена priority (PATCH/UI) | `priority_changed` | `{before:{priority}, after:{priority}}` |
| правка title/description/category | `fields_updated` | `{before:{изменённые поля}, after:{изменённые поля}}` |
| In Progress→Resolved | `resolved` | `{before:{status:"In Progress", resolution:null}, after:{status:"Resolved", resolution}}` |
| POST comment | `commented` | `{after:{comment_id, text}}` |

- HIS-1: один PATCH с несколькими изменёнными группами полей порождает по одному событию на тип (assigned / priority_changed / fields_updated); поля title/description/category агрегируются в одно `fields_updated`.
- HIS-2: переход в Resolved порождает только `resolved` (без дублирующего `status_changed`).
- HIS-3: no-op операции (без фактических изменений) событий не порождают.
- HIS-4: чтение (GET) событий не порождает.
- HIS-5: actor и created_at заполняются сервером; клиент не управляет историей.

## 7. Требования к UI (Jmix Flow UI; ориентир — docs/ui-concept.png)

- **UI-0 (layout):** тёмный сайдбар: Дашборд, Инциденты, Пользователи; шапка с селектором текущего пользователя. Пункт макета «Настройки» в MVP не входит (Q-11). Локаль интерфейса — ru (метки как в макете); метки сущностей/enum локализованы (en,ru).
- **UI-1 (реестр):** KPI-карточки (открытые, новые, в работе, критические, решено сегодня); строка поиска по ID/названию; фильтры «Все статусы»/«Все приоритеты»; таблица: ID, название, приоритет-бейдж с цветом, статус-бейдж, ответственный; кнопка «Новый инцидент»; сортировка created_at desc; пустые состояния; клик по строке открывает карточку.
- **UI-2 (карточка):** номер + название, бейджи; табы «Информация / История / Комментарии»; информация: статус, категория, описание, ответственный, даты, resolution; действия только допустимых переходов («Взять в работу», форма resolve с обязательным resolution, «Закрыть»); смена assignee селектором; форма комментария; для Closed — read-only, действий и формы комментария нет, видимое пояснение.
- **UI-3 (создание):** поля title, description, category, priority, assignee; клиентская валидация длины title (5–120) до отправки; ошибки сервера — понятным текстом; после сохранения — переход к карточке/реестру с обновлёнными данными.
- **UI-4 (dashboard):** KPI (открытые, новые, в работе, критические, решено сегодня); диаграмма по приоритетам (Charts add-on); график динамики «создано/решено» (Charts add-on, период — Q-05); недавняя активность (10 событий); нулевые/пустые состояния без ошибок рендера.
- **UI-5 (пользователи):** список-просмотр (id/имя/роль), без редактирования.
- **UI-6 (ошибки/пустота):** все серверные ошибки показываются пользователю (notification с текстом detail); пустые состояния во всех списках/табах; тихих падений нет.
- **UI-7 (бейджи):** цвета приоритетов: Critical — красный, High — оранжевый, Medium — жёлтый, Low — синий/нейтральный; статусы: New — синий, In Progress — янтарный, Resolved — зелёный, Closed — серый (точные токены темы фиксирует frontend).
- **UI-8 (время):** отображение меток времени согласовано с UTC-хранением (предложение: UTC с явной пометкой; Q-04/Q-15).

## 8. Нефункциональные требования и данные

- NFR-1: запуск `docker compose up -d db` + `./gradlew bootRun`; UI и REST на :8080; миграции Liquibase применяются при старте.
- NFR-2: demo-seed по `SEED_DEMO=true` (свойство `app.seed-demo`): 3–5 пользователей (engineer/manager), несколько инцидентов во всех статусах, включая Critical и решённый сегодня (с корректной историей); состав — предложение Q-14.
- NFR-3: тесты: ≥1 backend-тест на каждый эндпоинт; ≥3 на автомат (успех, 409, обязательность resolution); неизменяемость Closed; автозапись истории; сходимость dashboard с БД; ≥1 E2E-сценарий (создать → назначить → взять в работу → resolve → закрыть; комментарий и история видны). БД тестов — HSQLDB.
- NFR-4: `./gradlew build` зелёный локально и в CI; существующие тесты не ослабляются.
- NFR-5: README описывает запуск, миграции, demo-данные, тесты.
- NFR-6: ответы REST snake_case; время UTC; без пагинации; без DELETE.
- NFR-7: бизнес-правила в сервисном слое backend (переиспользуются UI и REST), не только в контроллерах/UI.
