# Чек-лист приёмки (DoD) — IT Incident Tracker (MVP, Jmix)

Тикет: DMI-14 (analyst). Сопоставление Definition of Done (TASK.md §7) и критериев `docs/requirements.md` с будущими тестами/сценариями для backend (DMI-16/17), frontend (DMI-18/19), QA (DMI-20).

Идентификаторы тестов ниже — **предложения analyst**: QA/backend фиксируют фактические имена классов/методов, сохраняя покрытие по смыслу (трассируемость по AC-идентификаторам). Статусы проставляет QA при приёмке.

## 0. Как прогонять проверки

| Команда | Что проверяет |
|---|---|
| `docker compose up -d db` | PostgreSQL 16 поднят |
| `./gradlew bootRun` | приложение (UI + REST) на :8080, миграции Liquibase применены |
| `./gradlew test` | backend/UI-тесты (HSQLDB, Postgres не нужен) |
| `./gradlew build` | полная сборка + тесты (обязательно зелёный локально и в CI) |
| `cd e2e && npm ci && npx playwright test` | E2E против запущенного приложения |
| `SEED_DEMO=true ./gradlew bootRun` | demo-данные (пользователи, инциденты разных статусов, Critical, решённый сегодня) |

## 3. E2E-сценарии (Playwright, e2e/)

### E2E-01 (обязательный, TASK.md §5) — полный цикл через UI
Предусловие: приложение запущено (db + bootRun), seed или чистая БД; в селекторе выбран пользователь-инженер.
1. Открыть реестр; нажать «Новый инцидент»; заполнить title (валидный), description, category, priority; сохранить.
   Ожидание: инцидент появился в реестре с ID `INC-NNN`, статус-бейдж New; открылась карточка (или переход из реестра).
2. В карточке назначить ответственного (селектор assignee).
   Ожидание: ответственный отображается; в табе «История» событие `assigned` с «было/стало» и актёром = выбранный пользователь.
3. Нажать «Взять в работу».
   Ожидание: статус-бейдж In Progress; событие `status_changed` в истории; кнопка «Взять в работу» исчезла.
4. Добавить комментарий в табе «Комментарии».
   Ожидание: комментарий виден с автором = выбранный пользователь; событие `commented` в истории.
5. Открыть форму resolve; попытаться сохранить без resolution → клиентская/серверная ошибка, статус не меняется; заполнить resolution и сохранить.
   Ожидание: статус Resolved; resolution виден в информации; событие `resolved` в истории.
6. Нажать «Закрыть».
   Ожидание: статус Closed; карточка read-only (нет действий/формы комментария); событие `status_changed` (Resolved→Closed).
7. Проверить таб «История»: полный набор событий цикла (created, assigned, status_changed, commented, resolved, status_changed) с payload «было/стало».
8. Проверить dashboard: KPI изменились согласованно (в работе/решено сегодня/открытые), недавняя активность содержит события цикла.

### E2E-02 (рекомендуемый) — серверная защита через UI
Создать инцидент (New); убедиться, что кнопки «Закрыть»/«Решить» недоступны; прямой REST-вызов New→Closed из теста → 409 (или UI-проверка отсутствия действий + backend-тест BT-11).

### E2E-03 (рекомендуемый) — поиск/фильтры и пустые состояния
Реестр: поиск по ID и по подстроке названия; фильтр статус+приоритет; заведомо пустой результат → пустое состояние с текстом.

## 6. Правила ведения чек-листа

- QA (DMI-20) проставляет статусы и фактические имена тестов, сохраняя ссылки на AC.
- Пункт DoD считается закрытым только при зелёном автотесте/сценарии и пройденной ручной проверке (если указана).
- Расхождения контракта, закрытые architect в ADR (Q-01…Q-15), обновляют ссылки AC, но не снижают покрытие.
